## Compact Rules

### design-system
- Write one `.md` per component under `docs/` (PascalCase, e.g. `Button.md`).
- Shared files: `Tokens.md`, `Patterns.md`, index at `docs/CLAUDE_DESIGN.md`.
- Extract variants/sizes from `cva()` definitions ONLY — never invent options.
- Copy CSS tokens verbatim from `src/App.css`; do not reorder or translate names.
- If a component was deleted, remove its orphan `.md` file.
- `CLAUDE_DESIGN.md` index: grouped by UI / Compuestos / Iconos / Tokens / Patrones, alphabetical within groups.
- Language: Spanish. File names in PascalCase.
- Trigger also when user says: "regenerar docs del design system", "sincronizar la guía", etc.
- Do NOT touch any file outside `docs/`.

### branch-pr
- Always check for an existing GitHub issue before creating a PR; link it.
- PR title must follow conventional commits format.
- Keep PR body concise: summary, motivation, and testing notes only.
- Never push directly to main/master without a PR.

### chained-pr
- Use when estimated diff exceeds 400 lines or when changes span unrelated concerns.
- Each PR in the chain must be independently reviewable and mergeable.
- Use stacked-to-main or feature-branch-chain strategies based on team preference.
- Each slice needs a clear start/finish/rollback boundary.

### work-unit-commits
- One logical change per commit; tests and docs travel with the code they cover.
- Conventional commits format required (feat, fix, refactor, test, docs, chore).
- Never use --no-verify. Never skip hooks.
- Split large changes into reviewable units before committing.

### issue-creation
- Search for duplicates before creating a new issue.
- Issues must include: context, expected behavior, actual behavior, reproduction steps (for bugs).
- Use labels consistently. Link related PRs and issues.

### comment-writer
- Warm and direct tone; lead with the point, follow with reasoning.
- Use "I noticed…" or "Consider…" rather than commands.
- Distinguish blocking from non-blocking feedback explicitly.
